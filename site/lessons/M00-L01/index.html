M00-L01 / ДИАГНОСТИКА / 35 МИН

Кто собирает код,
а кто его запускает?

На сервере работает Orders.dll. Вы копируете туда исходники, вводите dotnet build и получаете ошибку о недостающем SDK. Как оба наблюдения могут быть верными?

Что понадобится

Умение открыть терминал и перейти в папку проекта. Для симуляторов достаточно браузера. К концу урока вы сможете определить выбранный SDK, найти установленную среду выполнения и проверить, какую сборку запускаете.

Две роли одной команды

SDK (Software Development Kit) — набор инструментов разработчика. Он читает проект, восстанавливает зависимости и запускает компилятор. Runtime — среда, которая исполняет уже собранное приложение. Установка SDK обычно приносит и runtime.

Представьте две папки. В первой лежат Program.cs и файл проекта .csproj. После сборки во второй появляется OrderProbe.dll. Изменение текста в первой папке само по себе не меняет файл во второй.

ЭКСПЕРИМЕНТ 01

Соберите среду для задачи

Цель проекта — net11.0. В модели используется обычная framework-dependent сборка. Готовая DLL уже есть. Выберите установленный комплект и операцию.

Что происходит при сборке

  1. CLI выбирает SDK. На выбор влияет global.json в текущей папке или выше.
  2. MSBuild читает TargetFramework. Значение net11.0 задаёт целевую платформу. При необходимости build выполняет restore — восстановление зависимостей.
  3. В обычном проекте компилятор записывает IL (Intermediate Language, промежуточный язык) и метаданные в DLL. Runtime загружает сборку, а JIT преобразует нужные методы в машинный код.

Минимальный пример

// Program.cs
Console.WriteLine("Orders online");

Из каталога проекта выполните:

dotnet build
dotnet run --no-build

Ожидаемый вывод приложения — Orders online. Первая команда создаёт сборку. Вторая запускает артефакт выбранной конфигурации. При обычном dotnet run CLI при необходимости обновляет сборку.

ЭКСПЕРИМЕНТ 02

Какую версию вы запустите?

Начните с готовой сборки v1. Измените исходник и выполните запуск. Затем соберите проект и повторите запуск. Сравните три строки состояния.

Что проверить в реальном проекте

dotnet --version сообщает выбранный SDK. dotnet --list-sdks перечисляет установленные комплекты для архитектуры вызванного dotnet. dotnet --list-runtimes перечисляет среды исполнения. Версии 11.0.100 и 11.0.0 могут относиться к одной установке.

Production. Для веб-приложения может потребоваться ASP.NET Core Runtime. Self-contained публикация поставляет runtime с приложением. Эти два сценария выходят за рамки первого симулятора.

Частая ошибка

После смены Debug на Release команда запуска ищет другой артефакт. При расследовании запишите рабочую папку, TFM и конфигурацию.

Самостоятельная лабораторная

Вы выясняете, почему коллеги видят разный текст при запуске OrderProbe. Начните с пустой папки. Все действия относятся только к этому учебному проекту.

  1. Откройте PowerShell или терминал в новой пустой рабочей папке. Запустите по очереди dotnet --version, dotnet --list-sdks и dotnet --list-runtimes. Сохраните выбранный SDK и строки Microsoft.NETCore.App. Пути с именем пользователя можно убрать.
  2. До сборки запишите прогноз: позволит ли выбранный SDK собрать net11.0? Если SDK 11 доступен, создайте тестовый проект командой dotnet new console -n OrderProbe -f net11.0. Перейдите в папку OrderProbe. Выполните dotnet build, затем dotnet run --no-build.
  3. Измените текст, который печатает Program.cs. До эксперимента запишите прогноз для dotnet run --no-build. Выполните команду, затем dotnet run. Сравните вывод.
  4. Передайте на review версии, прогноз, фактический вывод двух запусков и объяснение в 2–3 предложениях. Если команда недоступна или выбран SDK старше по возрасту, пришлите первую ошибку и объясните, на каком этапе остановились. Отсутствие SDK — допустимый диагностический результат.

Критерий завершения. Другой разработчик сможет повторить ваши действия и объяснить результат по вашим наблюдениям. В M00 оцениваем исходную точку без проходного балла.

Проверка понимания

Сначала сделайте прогноз.
