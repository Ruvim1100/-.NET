Как исходный код C# становится работающей программой?

Сначала есть исходник

В файле лежит текст.

Четыре понятия — один процесс

Компилятор C#

Читает C# и создаёт IL (Intermediate Language — промежуточный язык) и метаданные о типах и методах.

Assembly · сборка

DLL содержит IL и метаданные. Это не текст Program.cs и, в типичном случае, ещё не готовые инструкции процессора.

CLR · Runtime

Среда исполнения загружает сборку, разрешает зависимости, управляет выполнением и памятью.

JIT · Just-in-Time

В типичном сценарии превращает нужные методы IL в машинный код во время исполнения. Не путай его с компилятором C#.

Зачем нужны команды build, run и publish?

  

    
dotnet build
Собирает проект и его зависимости. Создаёт файлы сборки, но само приложение не запускает.

    
dotnet run
Удобен при разработке: использует проект, при необходимости собирает его и запускает. Флаг --no-build пропускает сборку.

    
dotnet TraceFlow.dll
Запускает уже собранную framework-dependent DLL через установленный совместимый Runtime и нужные файлы приложения.

    
dotnet publish
Готовит комплект приложения с зависимостями для размещения на другой машине или сервере. Это следующий уровень после обычной сборки.

  

  
Глубже: когда JIT может не понадобиться?
Общая схема «C# → IL → JIT → машинный код» подходит для нашего обычного консольного примера. Однако ReadyToRun может заранее содержать машинный код для части методов, а Native AOT компилирует приложение заранее без JIT при выполнении. В этом уроке мы не смешиваем эти режимы с обычной сборкой.

  
Типичные ошибки при диагностике
Папка bin/Debug/net11.0 зависит от TFM, конфигурации и настроек проекта. Нельзя считать, что там всегда один файл DLL: обычно есть файлы для Runtime и зависимостей. Не путай папки bin (артефакты) и obj (промежуточные файлы). Для настоящего распространения приложения используй publish, а не случайную копию DLL из Debug.





  
ПРАКТИКА · POWERSHELL · .NET 11

  
Лабораторная: найти путь от текста до исполнения

  
Работай в новой безопасной папке — проект TraceFlow не должен менять прошлую работу. Прежде чем вводить команду, сделай прогноз и запиши его в форму ниже. Если версия SDK 11 недоступна, сохрани первую ошибку вместо выдуманного результата.

  
    
    
  1. Создай проект и собери.
    dotnet new console -n TraceFlow -f net11.0
cd TraceFlow
dotnet build
    Запиши путь сборки из терминала.
    2. 
    
  2. Рассмотри файлы результата.
    Get-ChildItem .\bin\Debug\net11.0\ | Select-Object Name
Get-Content .\bin\Debug\net11.0\TraceFlow.runtimeconfig.json
    Найди DLL и .runtimeconfig.json. Объясни, за что они отвечают.
    3. 
    
  3. Запусти готовую DLL напрямую.
    dotnet .\bin\Debug\net11.0\TraceFlow.dll
    Запиши фактический вывод. Это запуск готового артефакта, а не исходного .cs.
    4. 
    
  4. Измени Program.cs так, чтобы он печатал Trace: updated. Сохрани. Сначала предскажи, что выведет прямой запуск DLL без сборки, затем проверь:
    5. 
  

  
dotnet .\bin\Debug\net11.0\TraceFlow.dll
dotnet build
dotnet .\bin\Debug\net11.0\TraceFlow.dll

  
Критерии: представь реальные команды/логи, прогноз и факт до/после пересборки, названия артефактов и собственное объяснение цепочки C# → IL → Runtime/JIT → вывод. Для M00 это диагностика без проходного балла.

  
Дополнительный опыт (необязательно): dotnet publish -c Release и сравнение содержимого bin/Release/net11.0/publish с папкой Debug.
