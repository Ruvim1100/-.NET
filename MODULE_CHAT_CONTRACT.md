# Контракт модульного чата

1. Каждый модуль начинается в отдельном чате. Внутри модуля допустимы новые чаты для отдельного урока или продолжения незавершённой работы. Восстанови состояние по GitHub и [Tracker](https://docs.google.com/spreadsheets/d/18v_Rhc5ymrf2IoMg4E77suxVbFPU7DUBtzFLTiOjgRQ/edit). Найди последнюю подтверждённую попытку, сопоставь с каталогом и зависимостями.
2. Перед модулем обнови тематические официальные источники. Перед уроком прочитай API, примеры, ограничения и breaking changes. Укажи версии и дату.
3. Planned означает план. Published требует наличия HTML в GitHub. Личное Studied означает, что ученик изучил материал и прислал работу. Verified требует review, исправлений, объяснения и записи в таблице. Статус публикации сайта проверяй отдельно через Actions.
4. Уже опубликованный урок открывай повторно. До Verified предыдущего создание следующей страницы запрещено. В M00 фиксируй наблюдения и пробелы без проходного балла.
5. На review привязывай каждое замечание к примеру, последствию и повторной проверке. Веди Assessment History по попыткам; Lessons отражает текущий результат. Для пробела назначь дату повторения и новый пример. После записи перечитай диапазоны. Частичную запись восстанови по ID урока и попытки без дублей.
6. При отсутствии доступа к прогрессу проводи доступную проверку, сохраняй статус неподтверждённым до сверки. Публичные файлы содержат только программу и материалы.
7. Для каждой страницы применяй стандарт оформления из PROJECT_INSTRUCTIONS.md, расширяй браузерные проверки для новых взаимодействий, просматривай снимки. Для выпуска сверь SHA с успешным Academy / verify, используй проверенный артефакт и дай ссылку на открывающийся HTML.
8. Дай новичку пройти механизм по одному изменению за шаг: понятный старт, прогноз, наблюдение, причина, повтор, самостоятельный опыт. Проверяй, что первый шаг выполним до знакомства с внутренними терминами.

9. Для каждого нового модуля и урока применяй раздел «Стандарт оформления и допуска к публикации». Проверь маршрут от цели модуля до первого действия и от пошагового примера до самостоятельного эксперимента.

10. В каждом уроке должна быть полноценная форма для ответов и результатов практики и две работающие операции: «Собрать и скопировать отчёт» и «Сбросить ответы». Отчёт включает ID/версию урока, полный текст каждого вопроса и ответ ученика, код, команды, прогнозы, наблюдения и незаполненные поля. Копирование сопровождается предпросмотром и ручным резервным вариантом; сброс требует подтверждения. Не отправляй ответы в сеть автоматически и не записывай их в публичный репозиторий. Перед публикацией тестируй формирование/копирование/сброс в браузере. После вставки отчёта учеником в чат начинай с Code Review; сам отчёт не означает Studied или Verified без проверки и записи в Tracker.

## Передача незавершённого урока

При просьбе о переносе или перед согласованным завершением длинного чата сохрани в приватном Tracker ID урока, сделанный шаг, ссылку или выдержку из работы, открытые замечания и конкретное следующее действие. Для начатой попытки дополни её комментарий в Assessment History; до сдачи работы используй поле «Замечания» соответствующего модуля в Labs с явным ID урока. Сохрани прежнюю историю и перечитай запись. Перенос сам по себе не меняет статус и не создаёт новую попытку.

В новом чате найди именно эту запись и нужную версию материалов. Если ученик приложил исправление в первом сообщении, сравни его с последними замечаниями. Если источники расходятся, проверь дату, ID, evidence и последнюю попытку; при неоднозначности задай один конкретный вопрос. Уже установленный прогресс и существующую страницу используй повторно. Публикацию проверяй по успешному deployment и открывающейся ссылке GitHub Pages.
